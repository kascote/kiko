1. What Plume is (and what it leaves out)

Plume lays out user interfaces on a cell grid — the character grid of a terminal. You give it a tree of nodes (“put a border around a column of two text lines”) and a rectangle to work in; it decides where every box goes and tells a drawing target what to draw. That is the whole job: geometry in, drawing instructions out.

Just as important is what Plume deliberately does not do:

  • It never talks to a terminal. Drawing goes through an abstract Surface that the caller provides. Tests provide a RecordingSurface that just collects the calls; a real backend provides one that writes into a screen buffer.
  • It never measures text itself. “How many cells does this string occupy?” is the one question that depends on the terminal (some characters are two cells wide), so the answer is injected as a TextMeasurer.
  • It knows nothing about colors or styles. Every node carries an opaque value of type T — the paint token — that the engine passes through to the surface untouched, like a sticker it carries but never reads. Only the surface, at the far end, interprets it.
  • It keeps no state between frames. Every frame the caller builds a fresh tree and runs it through the same passes. There is no retained tree, no dirty-tracking, no cache to invalidate. Even scrolling is stateless from Plume’s point of view (§9).

All coordinates are whole cells — plain Dart ints. There are no fractional sizes, which is why you will see integer division (~/) and explicit “who gets the leftover cell” policies throughout the code.

The name “solver-free” in the package description means there is no constraint solver: no system of equations relating all the boxes, solved globally (the approach used by, e.g., Cassowary-based layout systems). Instead each parent makes a local decision — “given the room I was offered, here is the room each child gets” — in one walk down and up the tree. If you know Flutter’s box model this is the same idea; if you don’t, the next three sections are all you need.

In the code: the package summary is the library doc of packages/plume/lib/plume.dart; the node base class with the four passes is lib/src/render/render_node.dart (RenderNode).

2. A short vocabulary

Ten words cover everything. Each is defined here once, in plain terms, and used consistently after that.

cell
One character position on the terminal grid. The unit of every coordinate and size.
node / tree / leaf
A node is one box in the layout (RenderNode). Nodes with children form the tree; a node with no children is a leaf. Leaves are the ones that actually draw (text, spacers); everything above them only arranges.
constraint
The size limits a parent hands a child: minimum and maximum width, minimum and maximum height (BoxConstraints). “You may be 0 to 25 cells wide and exactly 2 tall.” A child must pick a size inside those limits.
unbounded
A constraint axis with no maximum (maxW or maxH is null): “be as wide/tall as you like.” Normal in the middle of a tree — a column asks each child for its natural height this way.
natural size
The size a node picks when nothing forces it bigger: a text line is as wide as its characters, a padded box is its child plus the padding.
paint token
The opaque style value T attached to text runs, borders, and fills. Plume carries it; the surface interprets it. In kiko it is a style object; in Plume’s own tests it is literally a String.
draw intent
One drawing instruction emitted during paint: “draw this text at (x, y)”, “fill this rectangle”, “draw a border around this rectangle”. The paint pass produces a stream of these — it never touches pixels or cells itself.
clip
The region a node is allowed to draw in. Anything a node tries to draw outside its own box (or any ancestor’s box) is trimmed or dropped.
grapheme cluster
What a reader perceives as one character — a letter, an accented letter, an emoji — even when it is several Unicode code points. All text handling works cluster by cluster, because a cluster is the smallest thing you can put in a cell (or two cells, for wide characters).
viewport
A window onto content taller than itself — the mechanism behind scrolling.

One notation note: rectangles are half-open. A Rect at x = 0 with width = 3 covers columns 0, 1, 2 — column 3 is outside. right and bottom are the first column/row past the edge. This convention makes widths add up without ±1 adjustments and is used everywhere (lib/src/geometry/rect.dart).

3. One frame, four passes

Every frame does the same thing. The caller builds a fresh tree of nodes, then drives it through three passes in one call; the fourth pass runs later, per input event:

  1. layout — each node picks its size within the limits its parent gave it, sizing its children along the way. Constraints flow down, sizes flow up. After this pass every node knows how big it is and where its children sit relative to itself — but nothing knows its absolute position yet.
  2. place — a cheap recursive walk turns those relative offsets into absolute rectangles on the grid.
  3. paint — each node emits its draw intents, then its children paint on top, all clipped to the boxes layout assigned.
  4. hitTest / tagAt — when input arrives, find the node (or the logical widget) under a point, using the rectangles the last frame fixed.

The driver really is this small (lib/src/render/render_frame.dart):

void renderFrame<T>(RenderNode<T> node, Rect area, Surface<T> surface,
    {TextMeasurer measurer = const MonospaceMeasurer()}) {
  node
    ..layout(BoxConstraints.tight(area.size), LayoutContext(measurer: measurer))
    ..place(area.topLeft)
    ..paint(surface);
}

The root is laid out tight to the frame area — it must be exactly that size — and hit testing is left to the caller, because it belongs to the input path, not the render path.

In the code: renderFrame in lib/src/render/render_frame.dart; the four pass methods are RenderNode.layout, .place, .paint, .hitTest in lib/src/render/render_node.dart.

4. Layout: constraints down, sizes up

This is the heart of the engine, and it is one rule applied recursively:

A parent hands each child a BoxConstraints — the box of allowed sizes. The child picks a Size within it (consulting its own children the same way first) and reports it back. The parent then decides where each child sits inside itself.

A BoxConstraints is four integers: minW, maxW, minH, maxH, where a null maximum means “unbounded — as large as you like.” Three named shapes cover most uses:

  • BoxConstraints.tight(size) — min equals max: “be exactly this size.”
  • BoxConstraints.loose(size) — zero up to size: “anything up to this.”
  • BoxConstraints.unbounded() — no limits at all.

Parents derive child constraints from their own using a small toolkit on BoxConstraints (lib/src/geometry/box_constraints.dart): deflate(h, v) shrinks the space to leave room for chrome like borders and padding; loosen() drops the minimums to ask a child for its natural size; enforce(outer) clamps one set of constraints inside another, so a widget can tighten what its parent allowed but never escape it; constrain(size) clamps a size into range — implementations call it before returning, which upholds the central invariant: a node’s reported size always satisfies the constraints it was given.

Three things in that picture are worth pausing on:

  • The parent never looks inside a child. All it learns is the returned size. A column doesn’t know whether a child is text, a bordered box, or a whole sub-application.
  • The child never knows where it will be. During layout, the parent stores each child’s position relative to itself in child.offset. Absolute positions don’t exist until the place pass.
  • Unbounded is normal. The column asks “how tall would you naturally be at up to 25 wide?” by handing down an unbounded height. Only a few combinations are actual errors, and those fail loudly (see the Flex rule in §10).

The node protocol

Every node type implements one method, performLayout. The public layout is a thin, non-overridable wrapper that (a) asserts the incoming constraints are well-formed — every layout in the app passes through this single funnel, so a negative or inverted range fails immediately in debug builds at zero release cost — and (b) records the result in size:

// RenderNode (render_node.dart), simplified:
Size layout(BoxConstraints constraints, LayoutContext context) {
  assert(constraints.isNormalized, ...);
  return size = performLayout(constraints, context);
}

A complete real node is small. This is all of Padding (lib/src/widgets/padding.dart):

Size performLayout(BoxConstraints constraints, LayoutContext context) {
  final childSize =
      child.layout(constraints.deflate(insets.horizontal, insets.vertical), context);
  child.offset = Offset(insets.left, insets.top);
  return constraints.constrain(
      Size(childSize.w + insets.horizontal, childSize.h + insets.vertical));
}

Shrink the room by the insets, lay the child out in what remains, shift it past the top-left insets, report child-plus-insets (clamped into the parent’s limits). Every other widget is this pattern with different arithmetic.

In the code: RenderNode.layout / performLayout in lib/src/render/render_node.dart; the constraint toolkit in lib/src/geometry/box_constraints.dart (tight, loose, deflate, loosen, enforce, constrain, isNormalized); LayoutContext in lib/src/render/layout_context.dart carries the one ambient input, the text measurer.

5. Place: from relative offsets to absolute rectangles

After layout, the tree holds sizes and parent-relative offsets. place is one mechanical walk that pins everything to the grid:

// RenderNode.place (render_node.dart) — not overridable:
void place(Offset origin) {
  _rect = Rect.fromOriginSize(origin, size);
  for (final child in children) {
    child.place(origin + child.offset);
  }
}

Each node’s absolute rect is its parent’s origin plus its own offset. There is no per-widget logic here at all — all placement decisions happened during layout; place just adds them up. The resulting rect is what paint draws inside and what hit testing reads later.

Keeping this pass separate is what lets layout stay position-free: a node sized deep inside a column would be laid out identically whether the column ends up at the top of the screen or the bottom.

6. Paint: draw intents and clipping

Paint walks the tree in order: a node first emits its own drawing (paintSelf — the default draws nothing), then its children paint on top, in list order, so the last child wins an overlap. The node’s rect is pushed as the active clip around all of it:

// RenderNode.paint (render_node.dart):
void paint(Surface<T> surface) {
  surface.pushClip(rect);
  paintSelf(surface);
  for (final child in children) {
    child.paint(surface);
  }
  surface.popClip();
}

The clip is a guarantee, not a suggestion: after a frame, no cell is written outside the intersection of a node’s rect with all of its ancestors’ rects. A node cannot draw outside the box layout gave it, and neither can anything below it.

The enforcement lives in ClippingSurface (lib/src/painting/clipping_surface.dart), the base class every concrete surface extends. It owns the clip stack (pushClip intersects with the current top, so the active clip is always the running intersection) and applies three per-call rules:

  • Fills and borders with no overlap with the clip are dropped. Otherwise they are passed through with the clip attached when the clip does not fully contain them — and a border always keeps its original rectangle. The backend drops the border cells that fall outside rather than drawing a shrunken border, which would fabricate a false edge along the clip line.
  • Text on a row outside the clip is dropped whole, with no measuring. Horizontal trimming, though, needs to know how wide each character is — knowledge the surface doesn’t have — so the leaf trims text to whole grapheme clusters before emitting (see trimToClip / paintClusterLine in lib/src/widgets/line_painter.dart), and the surface attaches the clip only as a backstop when a run starts left of it.
  • When the clip fully contains a draw call, the attached clip is null — an unclipped draw records exactly as it would if clipping didn’t exist, which keeps test goldens clean.

What comes out of the paint pass is a sequence of three intent kinds (lib/src/painting/draw_intent.dart): TextIntent (a run of characters at a cell), FillIntent (a filled rectangle), and BorderIntent (a border around a rectangle), each carrying its paint token and, if needed, the clip to honor. A RecordingSurface is nothing more than a list of these — which is exactly how Plume’s tests assert on rendering without any terminal.

In the code: RenderNode.paint / paintSelf in lib/src/render/render_node.dart; Surface in lib/src/painting/surface.dart; clip rules in ClippingSurface (lib/src/painting/clipping_surface.dart); intent types in lib/src/painting/draw_intent.dart; RecordingSurface in lib/src/painting/recording_surface.dart.

7. Hit testing and tags

When input arrives — a click at some cell — two questions come up, and Plume answers each with a small tree search over the rects the last place pass fixed. Neither runs during rendering; they run per event.

“Which node is under this point?” — hitTest

Descend the tree checking children front-to-back (the reverse of paint order), and return the first, deepest node whose rect contains the point. Because paint order is list order, the node drawn on top is found first — a click on an overlap lands on what the user actually sees.

Descent at each node is gated by that node’s own rect: a point outside a parent never reaches the parent’s children, no matter where a child was placed. This is deliberately independent of paint clipping — there is no accumulated clip stack here; each node prunes locally at its own box.

“Which widget is under this point?” — tagAt

The physically top-most node under a point is usually an anonymous leaf — a piece of text inside a button inside a form. To make hits mean something, whoever builds the tree can stamp any node with a tag: an opaque value (a widget id, in practice) that Plume never interprets, only compares. tagAt descends exactly like hitTest but reports the deepest tag it finds, falling back to the enclosing node’s own tag when nothing below carries one. That fallback is the whole point — hitTest(point)?.tag would land on the untagged leaf and answer null; tagAt answers “the button.”

Two smaller pieces round out the tag machinery:

  • nodeForTag(target) is the reverse lookup — find the node carrying a tag, then read its rect to anchor a popup to a widget or scroll it into view. Tags are assumed unique within a frame.
  • clipsHits is a per-node flag (false by default, true on Viewport) declaring “my rect clips whether my descendants are present at all.” Plume itself never consumes it — hitTest/tagAt already prune geometrically — it exists for a host layer that additionally tracks whether a widget is reachable (e.g. scrolled out of view) rather than merely what one point resolves to.
In the code: all in lib/src/render/render_node.dart — hitTest, tagAt, nodeForTag, the tag field, and clipsHits.

8. The two injected seams: TextMeasurer and Surface

Everything backend-specific enters through two small interfaces, both provided by the caller. This is why the engine runs identically under tests, a terminal, or anything else.

TextMeasurer — the one question about text

TextMeasurer (lib/src/painting/text_measurer.dart) has a single method: widthOf(text) — how many cells does this string occupy? It is injected once at the root (via LayoutContext) and threaded down to every node. Tests use MonospaceMeasurer, which counts every grapheme cluster as one cell; a terminal backend supplies one that knows CJK characters and emoji are two cells wide.

There is one contract to respect when implementing a measurer: widths must be additive over grapheme clusters — a string’s width must equal the sum of its clusters’ widths. The Text widget measures cluster by cluster and trims lines on those per-cluster totals; a measurer whose whole-string answer exceeds the per-cluster sum could let a run paint past its box. (Under-counting the whole string is merely wasteful: text over-reserves space.)

Line breaking, notably, is not in the measurer: it lives in the Text widget, because breaking needs the per-cluster paint tokens that a plain-string interface can’t carry. Width is genuinely the only backend-specific primitive.

Surface — where the drawing goes

Surface (lib/src/painting/surface.dart) is the sink: drawText, fillRect, drawBorder, plus the clip stack (pushClip/popClip/clipRect). It is also the one place the opaque paint token is interpreted. Concrete surfaces extend ClippingSurface and implement only the three raw sinks, so the clip rules of §6 can’t be bypassed or re-implemented inconsistently.

The test surface doubles as the testing story for the whole engine: paint into a RecordingSurface, and the recorded intent list — in call order — is the golden to assert on. No terminal, no snapshots of cells, just data.

9. Scrolling: the Viewport

Scrolling falls out of the pieces above with almost no new machinery. Viewport (lib/src/render/viewport.dart) shows a window onto a child taller than itself:

  • During layout it gives the child a tight width and unbounded height — “be exactly this wide, and as tall as you naturally are” — so the child reports its full content height.
  • It then places the child at Offset(0, -scrollOffset): scrolled content simply starts above the viewport’s top edge.
  • It sizes itself to whatever box its parent gave it.

And that’s it — no clipping code at all, because the ordinary paint pass already pushes the viewport’s rect as the active clip before descending: rows above or below the window are cut off by the same mechanism that clips everything else.

Two design points matter more than the mechanics:

  • Plume holds no scroll state. scrollOffset is a plain constructor argument the owner computes and clamps each frame. Since a fresh tree is built every frame anyway, there is nothing to reset or synchronize — scrolling is just building next frame’s tree with a different number.
  • Measurement flows out through a callback. The owner usually needs geometry to clamp that offset (“how tall is the content, really?”) or to scroll a widget into view. If given an onMeasure callback, the viewport reports a ViewportMetrics after each paint: its own height, the content’s full height, and every tagged descendant’s row range. Ranges are content-relative — measured from the top of the content, not the window — so they stay stable while scrolling.

Viewport is also the one node that overrides clipsHits → true, declaring to host layers that descendants scrolled outside its window should count as absent (§7).

In the code: Viewport, ViewportMetrics, ViewportTagRange in lib/src/render/viewport.dart. The layout trick is Viewport.performLayout; the tag walk is in its paintSelf.

The single-child wrappers

Four widgets do one constraint transformation each, and reading them together is the best way to internalize the layout protocol:

  • Padding — deflates the constraints, offsets the child past the insets, reports child + insets (shown in full in §4).
  • Align — lays the child out with loosened constraints (drop the minimums, ask for natural size), then itself fills every bounded axis and parks the child in the extra space per its Alignment (a nine-way enum: topLeft … bottomRight). On an unbounded axis it shrinks to the child instead. Center is Align(alignment: Alignment.center).
  • ConstrainedBox — applies its extra constraints enforced into the incoming ones: it can tighten a child but can never grant more than the parent allowed.
  • SizedBox — a leaf that asks for width × height, clamped to the constraints, and draws nothing. The idiomatic spacer.

Container: the decorated box

Container wraps one child with any mix of fixed sizing, padding, a background fill, a border, and edge labels (titles riding on the top or bottom edge). Its layout is the wrapper pattern with a little bookkeeping (Container.performLayout):

  • A border reserves one cell on all four sides. A label reserves its edge’s row even when there is no border, so a titled-but-borderless box insets its child exactly like a bordered one — the child never collides with the title.
  • width/height, when set, become tight constraints enforced against the incoming ones: the box takes that size regardless of its child, but still can’t exceed its parent.
  • Labels are laid out in a band between the corners. Labels sharing an edge and an alignment (start/center/end) pack together with a one-cell gap; an over-wide group is clamped so it never spills past a corner. A label’s content is an arbitrary node, not just a string.
  • Paint is fill, then border, then (as ordinary children) the child and the labels — so labels visibly sit on the border.

Flex (Row / Column): two passes over the line

Flex lays children along a main axis (horizontal for Row, vertical for Column) in two passes (Flex.performLayout):

  1. Measure the inflexible children with an unbounded main axis — each takes its natural main-axis extent — while the cross axis passes through the incoming limit.
  2. Share the leftover main-axis space among the Flexible children in proportion to their flex factors. Each gets free × flex ÷ totalFlex rounded down — except the last flexible child, which gets whatever remains, so rounding never leaks cells.

The knobs, all enums in flex.dart:

  • FlexFit — a tight child (what Expanded uses) must fill its allocated share exactly; a loose child (Flexible’s default) may be smaller.
  • MainAxisAlignment — where any still-remaining free space goes: packed at the start/end/center, or distributed as gaps (spaceBetween, spaceAround, spaceEvenly). Gap division has the same integer discipline: the remainder is handed out one cell at a time to the leading gaps, so the fill modes reach the trailing edge exactly.
  • CrossAxisAlignment — position each child across the line (start/center/end) or stretch it to fill.
  • MainAxisSize — whether the line fills the available main axis (max, the default) or shrink-wraps its children (min).
The one loud failure. A Flexible child needs bounded main-axis space to take a share of. Inside an unbounded main axis (say, an Expanded in a column inside a scroll viewport) there is no such space, and the child would silently collapse to zero cells. Flex throws a StateError for this — a real throw, deliberately not an assert, because asserts are compiled out under dart run and in AOT binaries, exactly the modes a real TUI app ships in, and invisible content with no error is the worst possible failure mode. (See the comment above the throw in Flex.performLayout.)

Stack, Positioned, Overlay: layers

Stack layers its children; the last paints on top and (per §7) wins hit testing. Children come in two kinds:

  • Non-positioned children are sized per StackFit (loose: up to the stack; expand: forced to fill) and parked in the stack’s extra space by its alignment. The stack sizes itself to the largest of them.
  • Positioned children are pinned: any mix of left/top/right/bottom distances and an explicit width/height. Setting both edges on an axis stretches the child to span between them; an axis with neither an edge nor a size falls back to the stack’s alignment. Like Flexible, Positioned is a marker the parent reads — its own layout just passes constraints through.

A stack whose children are all positioned sizes itself to the incoming constraints, and asserts they are bounded — with nothing to measure and no bound to fill, it would silently collapse (Stack.performLayout).

Overlay is a two-line subclass: Stack(children: [base, ...overlays], fit: StackFit.expand). The base is the main UI filling the frame; each overlay — modal, menu, tooltip — paints after it. Wrap an overlay in Positioned to anchor it (clicks outside it fall through to the base); leave it non-positioned to fill the frame as a blocking layer. This replaces ad-hoc “draw the popup last” ordering with the tree itself.

Text: clusters, wrapping, overflow

Text is the workhorse leaf. Its input is a flat list of TextRuns — pieces of string, each with one paint token. Layout flattens the runs into grapheme clusters, each carrying its token and its measured width (clusterRuns in line_painter.dart); every later decision — wrap, align, trim, emit — works on those clusters, never on raw strings, which is how wide characters and multi-code-point emoji stay intact.

  • Wrapping is opt-in (softWrap, default false). On a cell grid, a text that silently grows taller is a layout surprise, so by default a line shrink-wraps its natural width and long lines get overflow handling instead. With softWrap: true the text fills the offered width and wraps word by word; a single word wider than the box is hard-broken on whole clusters. Newlines in the input always start a new paragraph.
  • maxLines caps the line count at layout time.
  • align (start/center/end) positions each line within the node’s width. This is why a soft-wrapping text claims the full available width: so its lines have room to align inside it.
  • overflow is a paint-time choice for a too-wide line (only reachable with wrapping off): clip drops what doesn’t fit on whole clusters; ellipsis reserves the measured width of the … glyph — never an assumed 1 — and appends it in the style of the last surviving cluster.
  • At paint time the node emits at most rect.height rows — lines that couldn’t fit are never sent to be clipped — and merges consecutive same-token clusters back into single drawText calls, so styling granularity costs nothing at the surface.

line_painter.dart also exports the cluster utilities on their own, plus paintRuns — a one-call “paint a single styled line into a box” entry point for hosts that have a run list but no layout pass (a list row in a scrolled widget, for instance). Text itself doesn’t use it; it exists for callers outside a full Plume frame. Its skipColumns parameter implements horizontal scrolling by dropping leading display columns, again cutting only on whole clusters.

11. A frame, end to end

Plume’s own example (packages/plume/example/main.dart) ties every section together. The paint token here is literally String:

final tree = Container<String>(
  border: 'grey',
  child: Column<String>(
    children: [
      Text<String>([const TextRun('Hello, Plume', 'title')]),
      Text<String>([const TextRun('layout without a solver', 'body')]),
    ],
  ),
);

final surface = RecordingSurface<String>();
renderFrame(tree, const Rect(0, 0, 27, 4), surface);

surface.intents.forEach(print);

Walking the three passes with real numbers:

  1. Layout. The root Container gets tight(27×4). Its border reserves one cell per side, so the Column gets tight(25×2) (a deflate(2, 2)). The column measures its two inflexible children with width ≤ 25 and unbounded height: the texts report their natural sizes, 12×1 and 23×1. The column fills its tight box and reports 25×2, placing the texts at relative offsets (0, 0) and (0, 1); the container reports 27×4, placing the column at (1, 1).
  2. Place. Origins add up: container rect (0, 0, 27, 4), column (1, 1, 25, 2), texts (1, 1, 12, 1) and (1, 2, 23, 1).
  3. Paint. The container strokes its border; each text emits one run. Everything fits inside its clip, so no intent carries one.

The recorded output — the paint golden — is exactly:

drawBorder(Rect(0, 0, 27, 4), grey)
drawText(1, 1, "Hello, Plume", title)
drawText(1, 2, "layout without a solver", body)

Swap RecordingSurface for a buffer-backed one and the same three intents become cells on a real screen. Nothing about the tree changes — which is the architecture in one sentence.
